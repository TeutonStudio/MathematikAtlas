# v2.34.0 – Universeller SVG-Grafikknoten und Operatorenkatalog

## Status

Planung auf Basis von `master` nach v2.33.0.

Der bestehende Knotentyp `grafik.svg.knoten` wird **nicht durch viele einzelne SVG-Knotentypen ersetzt**. Stattdessen bleibt er der universelle SVG-Grafikknoten und erhält einen vollständigen, erweiterbaren Operatorenkatalog im bestehenden Operatorauswahldialog.

Der bestehende Datentyp `SvgGrafik` bleibt der durchgereichte, unveränderliche SVG-AST.

---

# 1. Zielbild

Der SVG-Grafikknoten verhält sich fachlich wie ein einzelner universeller Rechnerknoten für SVG:

```text
                 optionale Fachwerte
              Stil / Zahl / Text / ...
                        │
                        ▼
SVG-Grafik ───────► SVG-Grafikknoten ───────► SVG-Grafik
                       │
                       └─ Operator im Dialog
```

Jeder konstruktive oder bearbeitende SVG-Operator nimmt eine bestehende `SvgGrafik` entgegen, verändert sie nicht mutierend, sondern erzeugt einen neuen AST und gibt diesen wieder als `SvgGrafik` aus.

Ist kein SVG-Eingang verbunden, beginnt der Knoten mit `SvgGrafik.standard()` und darf somit selbstständig eine neue Grafik erzeugen.

Damit gilt durchgehend:

```text
SVG₀
 ↓
Operator A
 ↓
SVG₁
 ↓
Operator B
 ↓
SVG₂
 ↓
Operator C
 ↓
SVG₃
```

Ein Knoten repräsentiert genau **einen gewählten SVG-Operator**. Komplexe Grafiken entstehen durch Verkettung vieler SVG-Grafikknoten.

---

# 2. Verbindliche Invarianten

1. `SvgGrafik` ist der kanonische SVG-Datentyp des Atlas.
2. Die Grafik wird als strukturierter AST gespeichert, nicht als roher XML-String.
3. Jeder konstruktive/bearbeitende Operator besitzt einen SVG-Ausgang.
4. Der primäre SVG-Eingang heißt stabil `svg`.
5. Ein unbelegter primärer SVG-Eingang bedeutet `SvgGrafik.standard()`.
6. Ein Operatorwechsel verändert den Knotentyp nicht, sondern nur `svgOperator`, Anschlüsse und operatorspezifische Parameter.
7. Anschlussrollen besitzen stabile Identitäten. Position allein darf keine alte Edge auf eine fachlich andere Rolle umdeuten.
8. Der Operatorauswahldialog ist die einzige zentrale Auswahloberfläche für SVG-Operationen.
9. SVG-Semantik liegt im Rechenkern beziehungsweise in der SVG-Auswertung, nicht in Compose.
10. Der Inspector erklärt sowohl den gewählten Operator als auch dessen Wirkung auf den eingehenden AST.
11. Ein Operator darf keine vorhandenen AST-Bestandteile verlieren, sofern seine Semantik nicht ausdrücklich Entfernen/Ersetzen/Filtern lautet.
12. ID- und Referenzintegrität muss beim Kombinieren, Kopieren und Umbenennen erhalten bleiben.

# 3. Ablauf eines SVG-Grafikknotens

## 3.1 Erzeugen

Ein neu erzeugter SVG-Grafikknoten startet zunächst im Operator `Dokument`.

Er besitzt mindestens:

```text
svg : SvgGrafik?  ->  svg : SvgGrafik
```

Der Eingang darf leer bleiben.

Der Inspector zeigt direkt:

- aktuellen Operator,
- Kategorie,
- Kurzbeschreibung,
- Erklärung des Datenflusses,
- operatorspezifische Parameter,
- AST-Zwischenstand,
- später eine visuelle Vorschau.

## 3.2 Operator auswählen

Ein Klick auf den Operator öffnet den bestehenden großen Operatorauswahldialog.

Der Dialog erhält für SVG mindestens:

```text
Suche
Kategorien
Operatorliste
Symbol / Name
Kurzbeschreibung
Ein-/Ausgangsvorschau
Wirkung auf die Grafik
```

Beispiele:

```text
Grundformen
  Linie
  Rechteck
  Kreis
  Ellipse
  Polygon
  Linienzug

Transformation
  Verschieben
  Skalieren
  Drehen
  Matrixtransformation
```

## 3.3 Vorschau des Operatorwechsels

Vor Übernahme wird über den bestehenden Knotenersetzungs-/Vorschauvertrag gezeigt:

- welche Handles bleiben,
- welche neuen Handles entstehen,
- welche Handles entfallen,
- welche Edges erhalten bleiben,
- welche Edges inkompatibel würden.

Der primäre `svg`-Eingang und `svg`-Ausgang sollen bei allen normalen SVG-transformierenden Operatoren dieselben Anschluss-IDs behalten.

Weitere Rollen dürfen nur bei identischer Semantik ihre IDs behalten, zum Beispiel:

```text
stil -> stil
x    -> x
```

aber nicht allein deshalb, weil beide zufällig der zweite Eingang sind.

## 3.4 Auswertung

Sinngemäß:

```kotlin
val basis = eingangSvg ?: SvgGrafik.standard()
val operator = SvgOperatoren.finde(svgOperator)
val ergebnis = operator.ausführen(basis, eingänge, parameter)
return svg = ergebnis
```

Die konkrete Implementierung soll langfristig aus dem großen `when (operator)` in eine registrierte Operatorausführung überführt werden, sodass Metadaten, Anschlüsse, Inspectorbeschreibung und Auswertung nicht auseinanderlaufen.

## 3.5 Weiterreichen

Der Ausgang enthält den vollständigen neuen AST einschließlich:

- Dokumentraum,
- mathematischem Koordinatenraum,
- sichtbaren Elementen,
- Gruppenstruktur,
- Definitionen,
- IDs,
- Referenzen,
- Transformationen,
- Stilen.

Der nächste SVG-Knoten erhält genau diesen Zustand.

# 4. Zielarchitektur des Operatorregisters

Der heutige `SvgOperatorDefinition`-Ansatz wird zur zentralen Quelle der Wahrheit erweitert.

Bevorzugt sinngemäß:

```kotlin
data class SvgOperatorDefinition(
    val id: String,
    val titel: String,
    val symbolLatex: String,
    val kategorie: SvgOperatorKategorie,
    val beschreibung: String,
    val ablaufBeschreibung: String,
    val anschlüsse: List<AnschlussDaten>,
    val standardParameter: Map<String, String>,
    val wirkung: SvgOperatorWirkung,
)
```

`SvgOperatorWirkung` beschreibt für UI und Tests mindestens:

```text
Dokument erzeugen/ändern
Element ergänzen
Elemente bearbeiten
Transformation anwenden
Definition ergänzen
Grafiken kombinieren
Ausgabe/Inspektion
```

Die eigentliche Ausführung soll ebenfalls eindeutig an diese Definition gebunden sein, beispielsweise über eine Registry:

```kotlin
interface SvgOperatorAusführung {
    fun ausführen(kontext: SvgOperatorKontext): SvgOperatorErgebnis
}
```

Damit existiert nicht länger eine Liste im Dialog und eine zweite, manuell synchronisierte Wahrheit im Auswerter.

# 5. Geplanter SVG-Operatorenkatalog

Der Begriff „alle SVG-Methoden“ bedeutet für den Atlas die **deklarativen SVG-Fähigkeiten des strukturierten SVG-AST**, nicht Browser-DOM-Methoden wie `getBBox()` oder JavaScript-Ereignis-APIs.

Der Operatorenkatalog soll so vollständig angelegt werden, dass neue SVG-AST-Typen nur noch als neue Operatorregistrierungen ergänzt werden müssen.

## A. Dokument

### SVG-Dokument

Bestehend.

Wirkung:

```text
kein SVG-Eingang -> neues Dokument
SVG-Eingang      -> Dokumentparameter des bestehenden AST ändern
```

Parameter:

- ViewBox minX/minY/Breite/Höhe,
- mathematischer x/y-Koordinatenraum,
- Breite/Höhe,
- `preserveAspectRatio`.

Später ergänzbar:

- Metadaten,
- Titel/Beschreibung,
- Namespace-/Exportoptionen nur soweit fachlich nötig.

# 6. Grundformen

Bereits vorhanden beziehungsweise vollständig als Operatoren zu führen:

- Linie
- Rechteck
- Kreis
- Ellipse
- Polygon
- Linienzug

Alle besitzen:

```text
svg  : SvgGrafik?
stil : SvgStil?
... geometrische Argumente
-> svg : SvgGrafik
```

Die geometrischen Eingänge verwenden mathematische Koordinaten und werden zentral über `SvgKoordinatenraum` in SVG-Koordinaten abgebildet.

# 7. Pfade

## Pfad

Bestehend, aber intern weiter strukturieren.

Unterstützte Segmente:

- Move `M`
- Line `L`
- Cubic Bézier `C`
- Quadratic Bézier `Q`
- Arc `A`
- Close `Z`

Langfristig soll der Nutzer nicht auf einen einzelnen Rohtextparameter angewiesen sein.

Zusätzliche Operatoren beziehungsweise strukturierte Werte:

- Pfad beginnen
- Liniensegment ergänzen
- kubische Bézierkurve ergänzen
- quadratische Bézierkurve ergänzen
- Bogen ergänzen
- Pfad schließen

Bevorzugtes Modell:

```text
SvgPfadDaten -> Segment ergänzen -> SvgPfadDaten
```

und anschließend:

```text
SvgGrafik + SvgPfadDaten + Stil -> Pfad -> SvgGrafik
```

Damit bleibt der SVG-Grafikknoten selbst auf Grafikoperationen fokussiert, während komplexe Pfade strukturiert aufgebaut werden können.

Langfristige Textparameter:

- Schriftgröße,
- Schriftfamilie,
- Gewicht,
- Stil,

- Baseline,

Mathematische Beschriftungen behalten den LaTeX-Inhalt strukturiert, auch wenn die konkrete SVG-Ausgabe später über gerenderte Pfade/Glyphen erweitert wird.

# 9. Gruppen und Struktur

Operatoren:

- Gruppieren
- Gruppe auflösen
- Elemente kombinieren
- SVG kombinieren
- Element duplizieren
- Element entfernen
- Element ersetzen
- nach vorne
- nach hinten
- ganz nach vorne
- ganz nach hinten

Die heutige Operation `Gruppieren` fasst den bisherigen sichtbaren Inhalt zusammen. Für feinere Bearbeitung wird eine Elementauswahl/-referenz benötigt.

# 10. Elementreferenzen und Auswahl

Neue strukturierte Capability:

```text
SvgElementReferenz
```

Sie referenziert ein Element über eine stabile AST-Identität und nicht über Listenindex oder momentane Bildschirmposition.

Geplante Operatoren:

- Element nach ID auswählen
- zuletzt ergänztes Element auswählen
- Gruppe auswählen
- mehrere Elemente auswählen
- Auswahl vereinigen
- Auswahl filtern

Noch zu entscheiden ist, ob der erste Release bereits einen eigenen `SvgElementAuswahl`-Typ für Mehrfachauswahl einführt oder zunächst nur einzelne Referenzen unterstützt.

Wichtig:

- sichtbare IDs dürfen sprechend sein,
- interne Identität darf bei nötiger Kollisionsauflösung nicht verlorengehen,
- Referenzen müssen beim Kopieren/Kombinieren korrekt umgeschrieben werden.

---

# 11. Transformationen

Der Kern besitzt bereits strukturierte Transformationen:

- Verschieben
- Skalieren
- Drehen
- Matrix

Diese werden vollständig über den Dialog erreichbar gemacht.

Bevorzugtes Modell:

```text
SvgTransformation
```

als eigener Werttyp mit passenden Erzeugeroperatoren/-knoten.

Der SVG-Grafikknoten erhält dann den Operator:

### Transformieren

```text
svg            : SvgGrafik?
auswahl        : SvgElementReferenz / SvgElementAuswahl?
transformation : SvgTransformation
-> svg         : SvgGrafik
```

Ohne Auswahl muss die Semantik ausdrücklich festgelegt werden. Bevorzugt:

```text
ohne Auswahl -> gesamte eingehende Grafik als Gruppe transformieren
mit Auswahl  -> ausgewählte Elemente transformieren
```

Alternativ kann „gesamte Grafik“ als explizite Auswahl modelliert werden, um implizite Sonderfälle zu vermeiden.

Transformationen werden als AST-Transformation gespeichert und nicht vorzeitig in Koordinaten eingerechnet.

---

# 12. Stil

Der bestehende `SvgStil` bleibt eigener verbindbarer Wert.

Bereits enthalten:

- Füllung,
- Kontur,
- Konturbreite,
- Deckkraft,
- Strichmuster,
- Linienende,
- Linienverbindung.

Zu ergänzen:

- Füllregel,
- Konturdeckkraft,
- Fülldeckkraft,
- Dash-Offset,
- Miter-Limit,
- Textstilattribute,
- optional CSS-Klasse als Metadatum.

Der Grafikoperator `Stilisieren` erhält:

```text
svg      : SvgGrafik?
auswahl  : SvgElementReferenz / SvgElementAuswahl?
stil     : SvgStil
-> svg   : SvgGrafik
```

Daneben soll `SvgStil` selbst komponierbar werden:

```text
Stil -> Füllung ändern -> Stil -> Kontur ändern -> Stil
```

Dies sollte über Stiloperatoren erfolgen, nicht durch ein Aufblähen des SVG-Grafikknotens mit rein stilinternen Operationen.

---

# 13. Definitionen (`defs`)

Der Kern besitzt bereits `SvgDefinition` und `SvgSymbolDefinition`. Diese Architektur wird ausgebaut.

Geplante Definitionstypen:

- Symbol
- Marker
- LinearGradient
- RadialGradient
- ClipPath
- Mask
- Pattern
- später Filterdefinitionen

Der SVG-Grafikknoten besitzt für jede Definition einen Dialogoperator, der die Definition in `SvgGrafik.definitionen` ergänzt.

Beispiel:

```text
SVG + SymbolDefinition -> Symbol definieren -> SVG
SVG + SymbolReferenz   -> Symbol verwenden  -> SVG
```

Definitionen und ihre Referenzen müssen typisiert sein. `url(#foo)` soll intern nicht als beliebiger String die einzige Wahrheit bilden.

---

# 14. Wiederverwendung (`symbol` / `use`)

Operatoren:

- Symbol definieren
- Symbol verwenden (`use`)

`use` erhält mindestens:

- Symbolreferenz,
- Position,
- optionale Transformation,
- optionalen Stil/Overrides.

Dies ist insbesondere für mathematische Diagramme wichtig, etwa wiederverwendbare Punkt-, Pfeil-, Achsen- oder Markierungssymbole.

# 15. Marker und Pfeile

Operatoren:

- Marker definieren
- Marker an Start setzen
- Marker an Mitte setzen
- Marker an Ende setzen

Damit werden Pfeilspitzen nicht als Sonderfall einer mathematischen Linie hart codiert.

Ein Vektorpfeil kann später fachlich einfach eine Linie/Pfad plus Marker erzeugen.

- ClipPath definieren
- ClipPath anwenden

- Maske anwenden

# 20. Bilder und externe Ressourcen

`image` wird bewusst nach dem Referenz-/Sicherheitsmodell umgesetzt.

Geplante Operatoren:

- Bild einbetten
- Bild referenzieren

- nur lokale/eingebettete Ressourcen,

- externe URLs,

# 21. Metadaten und Barrierefreiheit

Geplante strukturierte Ergänzungen:

- Titel (`title`)
- Beschreibung (`desc`)
- Metadaten

Diese können sowohl Dokument- als auch Elementbezug besitzen.

Der Inspector soll bei relevanten exportierten Diagrammen auf fehlende Beschreibung hinweisen können, ohne sie zu erzwingen.

---

# 22. Animation

SVG-Animation wird zunächst nur im Katalog reserviert und **nicht** Bestandteil des ersten v2.34.0-Implementierungspakets.

Mögliche spätere Operatoren:

- animate
- animateMotion
- animateTransform
- set

Die statische `SvgGrafik`-Semantik darf dafür nicht nachträglich gebrochen werden. Animationen müssten als deklarative AST-Bestandteile gespeichert werden.

Keine JavaScript-/DOM-Ereignislogik im Rechenkern.

---

# 23. Ausgabe- und Inspektionsoperatoren

Nicht jede SVG-bezogene Funktion verändert die Grafik. Diese Operationen werden fachlich von den normalen `SVG -> SVG`-Operatoren getrennt.

Mögliche Ausgaben:

- SVG serialisieren -> Text
- Elementzahl -> Zahl
- Definitionenzahl -> Zahl
- ViewBox abfragen
- Elementreferenz suchen

Zu entscheiden ist, ob solche Abfragen ebenfalls Modi desselben SVG-Knotens werden oder eigene Reflexions-/Exportknoten erhalten.

Bevorzugt:

```text
SVG-Grafikknoten = konstruiert/bearbeitet SVG und gibt SVG aus
SVG-Abfrageknoten = liest SVG und gibt andere Datentypen aus
SVG-Exportknoten  = erzeugt Text/Datei/Renderergebnis
```

Damit bleibt der Hauptknotenvertrag verständlich.

# 24. Operatorauswahldialog

Der Dialog wird nach Kategorien strukturiert:

```text
Dokument
Grundformen
Pfade
Text
Struktur
Auswahl
Transformation
Stil
Definitionen
Wiederverwendung
Marker
Clipping & Masken
Verläufe
Pattern
Filter

```

Jeder Eintrag zeigt:

1. Name,
2. Symbol/Vorschau,
3. Kategorie,
4. Kurzbeschreibung,
5. Eingänge,
6. Ausgabe,
7. „Was passiert?“.

Beispiel `Kreis`:

```text
Kreis

Ergänzt dem eingehenden SVG einen Kreis im mathematischen
Koordinatenraum. Ist kein SVG verbunden, wird zuerst ein neues
Standard-SVG erzeugt.

Eingänge:
SVG? · Stil? · x · y · Radius

Ausgabe:
SVG

Ablauf:
1. Eingehenden AST übernehmen oder neuen AST erzeugen.
2. Mittelpunkt in den SVG-Viewport abbilden.
3. Radius über den Dokumentraum skalieren.
4. Kreis/Ellipse mit stabiler ID ergänzen.
5. Vollständigen neuen AST ausgeben.
```

Diese Ablaufbeschreibung soll aus den Operator-Metadaten stammen und nicht als Sondertext im Compose-Inspector dupliziert werden.

# 25. Inspector: Ablauf erklären

Der Inspector des gewählten Operators soll künftig explizit zwei Informationsblöcke besitzen.

## Operator

```text
Kreis
Grundformen

Ergänzt einen Kreis im mathematischen Koordinatenraum.
```

## Ablauf

```text
SVG-Eingang
  ↓
vorhandenen AST übernehmen
oder Standard-SVG erzeugen
  ↓
Koordinaten abbilden
  ↓
Kreis ergänzen
  ↓
SVG-Ausgang
```

Bei `Kombinieren` beispielsweise:

```text
SVG A ─┐
       ├─ IDs/Definitionen prüfen -> ASTs vereinigen -> SVG
SVG B ─┘
```

Bei `Stilisieren`:

```text
SVG + Auswahl + Stil
       ↓
ausgewählte Elemente kopieren
       ↓
Stil ersetzen/zusammenführen
       ↓
SVG
```

Damit kann der Nutzer nachvollziehen, ob der Operator ergänzt, ersetzt, gruppiert oder nur Dokumentmetadaten verändert.

# 27. IDs und Referenzintegrität

Der heutige AST kann IDs beim Kombinieren bereits eindeutig machen. Mit `use`, Marker, Gradients, ClipPaths, Masken und Filtern reicht ein bloßes Umbenennen der Definition jedoch nicht mehr.

Daher vor den erweiterten Definitionen einführen:

```text
SvgId
SvgReferenz<T>
```

oder einen äquivalenten strukturierten Vertrag.

Beim Kombinieren muss gelten:

```text
ID-Kollision erkennen
 -> neue ID vergeben
 -> alle Referenzen im übernommenen Teilbaum auf neue ID umschreiben
 -> Referenzintegrität prüfen
```

Tests müssen gebrochene `url(#...)`-/`use`-Referenzen verhindern.

---

# 28. Koordinatenräume

Der mathematische Koordinatenraum bleibt ein zentrales Atlas-Merkmal und wird von SVG-Pixel-/Viewport-Koordinaten getrennt.

Jeder geometrische Operator legt explizit fest, ob sein Parameter in

```text
mathematischen Koordinaten
SVG-/Viewport-Koordinaten
relativen SVG-Einheiten
```

interpretiert wird.

Standard für mathematische Grafikoperatoren:

```text
mathematische Koordinaten
```

Reine SVG-Spezialoperatoren dürfen später explizit einen SVG-Koordinatenmodus besitzen.

Keine stillschweigende Mischung beider Räume.

---

# 29. Fehler- und Warnmodell

Operatoren sollen strukturierte Fehler/Warnungen liefern.

Beispiele:

Warnung:

```text
Die kombinierten SVGs besitzen unterschiedliche Dokumenträume;
der erste Eingang bestimmt ViewBox und Koordinatenraum.
```

Fehler:

```text
Markerreferenz zeigt auf keine vorhandene Markerdefinition.
```

```text
Pfad benötigt mindestens ein Startsegment.
```

```text
Kreisradius darf nicht negativ sein.
```

Fehlertexte stammen möglichst aus der SVG-Semantikschicht und nicht aus Compose.

---

# 30. Persistenz und Migration

Bestehende Karten aus v2.33.0 müssen ohne Änderung weiter funktionieren.

Stabil bleiben insbesondere:

```text
grafik.svg.knoten
grafik.svg.stil
svgOperator
svg-Eingangsrolle
svg-Ausgangsrolle
bestehende Operator-IDs
```

Neue Operatoren erhalten neue stabile IDs.

Beim Operatorwechsel:

- kompatible Anschluss-IDs erhalten,
- fachlich andere Rollen nicht wiederverwenden,
- Undo/Redo atomar,
- JSON-Roundtrip stabil.

Der AST-Codec muss später alle neuen Definitionen, Referenzen und Transformationen verlustfrei abbilden.

# 31. Empfohlene Implementierungsreihenfolge

## Commit 1 – Operatorvertrag und Dialogmetadaten

- `SvgOperatorDefinition` um Ablauf-/Wirkungsmetadaten erweitern,
- Kategorie als stabilen Typ statt freier String prüfen,
- Inspector und Dialog aus derselben Definition speisen,

# 33. Abnahmekriterien für die erste Ausbaustufe

- [ ] Es existiert weiterhin genau ein universeller, separat erzeugbarer SVG-Grafikknotentyp für SVG-Operationen.
- [ ] Alle unterstützten SVG-Grafikoperationen sind zentral als Operatoren registriert und im Dialog auswählbar.
- [ ] Der Dialog erklärt Name, Kategorie, Eingänge, Ausgabe und Wirkung jedes Operators.
- [ ] Der Inspector erklärt den konkreten Ablauf des gewählten Operators.
- [ ] Jeder normale Grafikoperator folgt `SvgGrafik? + Argumente -> SvgGrafik`.
- [ ] Ein fehlender SVG-Eingang beginnt ein neues Standard-SVG.
- [ ] Der SVG-AST wird vollständig und unveränderlich von Knoten zu Knoten weitergereicht.
- [ ] Operatorwechsel erhalten kompatible SVG-Edges und entfernen keine Edges stillschweigend.
- [ ] Operator-Metadaten und Ausführung können nicht auseinanderlaufen.
- [ ] Transformationen werden über den Operatorendialog erreichbar.
- [ ] Bestehende Elemente können über stabile Referenzen ausgewählt und nachträglich transformiert/stilisiert werden.
- [ ] Definitionen und Referenzen besitzen einen referenzsicheren Vertrag.
- [ ] `symbol/use` und Marker sind ohne rohe XML-Fragmente möglich.
- [ ] Kombinieren erhält alle internen Referenzen trotz ID-Kollisionen.
- [ ] Der Inspector zeigt einen nachvollziehbaren SVG-Zwischenstand und später eine echte Vorschau.
- [ ] Bestehende v2.33.0-Karten bleiben migrationsfähig.

# 34. Offene Architekturentscheidungen vor Implementierung

1. **Auswahltyp**
   - zunächst `SvgElementReferenz` für genau ein Element,
   - oder direkt `SvgElementAuswahl` für 0..n Elemente?

2. **Transformation ohne Auswahl**
   - gesamte Grafik gruppieren und transformieren,
   - oder Auswahl zwingend verlangen?

3. **Sprechende IDs**
   - Benutzer darf explizite IDs wie `x-achse`, `graph-f`, `punkt-A` vergeben?
   - interne technische Identität zusätzlich getrennt halten?

4. **Definitionshandles**
   - ein gemeinsamer `SvgDefinition`-Handle,
   - oder spezialisierte Handles wie `SvgMarker`, `SvgGradient`, `SvgSymbol`?

   Bevorzugt: gemeinsamer Obertyp mit präzisen Untertypen im Typvertrag, sofern das Typsystem dies ohne unübersichtliche Anschlüsse unterstützt.

5. **Stilzusammenführung**
   - neuer Stil ersetzt den kompletten alten Stil,
   - oder nur gesetzte Felder überschreiben?

   Für komponierbare Stiloperatoren wird langfristig ein partieller Stil-/Patch-Vertrag wahrscheinlich benötigt.

6. **SVG-Abfragen**
   - Modi desselben Knotens mit abweichendem Ausgabetyp,
   - oder eigener SVG-Abfrageknoten?

   Bevorzugt: eigener Abfrageknoten, damit der Hauptvertrag `SVG -> SVG` stabil bleibt.

7. **Filterumfang v2.34.0**
   - nur Architektur vorbereiten,
   - oder bereits Basisfilter wie Blur/DropShadow implementieren?

8. **Mathematische Hochoperatoren**
   - Koordinatensystem, Achse, Gitter, Funktionsgraph bereits in v2.34,
   - oder erst nach Abschluss der generischen SVG-Infrastruktur?

   Bevorzugt: generische SVG-Infrastruktur zuerst stabilisieren; mathematische SVG-Komponenten darauf in der folgenden Version aufbauen.
