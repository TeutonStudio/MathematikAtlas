# ADR: G0.1 Erweiterbares Methodenfundament

- Datum: 2026-08-11
- Status: angenommen
- Grundlage: `2026-08-01-einheitliches-methodenmodell.md`

## Kontext

Das vereinheitlichte Methodenmodell hat `Methode` als einzigen fachlichen Oberbegriff etabliert und `Funktion`, `Abbildung` und `Prädikat` auf abgeleitete Klassifikationen reduziert. Die konkrete Implementierung war jedoch weiterhin eine finale Kotlin-`data class Methode`, die gleichzeitig Signatur, symbolische Vorschrift, mathematische Anwendung, Darstellung, Restriktionsherkunft und historische Mehrfachausgaben enthielt.

Für weitere Domänen, insbesondere spätere Script-/Engine-Methoden, ist diese Kopplung ungeeignet. Eine Scriptmethode darf nicht allein durch ihre Zugehörigkeit zu `Methode` die mathematische Semantik `ersetze(vorschrift, argumente)` erben.

## Entscheidung

1. `Methode` wird ein offener Obervertrag.
2. Die bisherige konkrete Mathematikimplementierung heißt `MathematischeMethode`.
3. `Funktion`, `Abbildung` und `Prädikat` bleiben ausschließlich abgeleitete Nutzerbegriffe. Es entstehen keine neuen physischen Klassen dafür.
4. `mathematik.methode` bleibt die einzige produktive Methoden-Anschlussart.
5. `SignaturtragendeMethode` kennzeichnet Methoden mit der heutigen mathematischen `MethodenSignatur`.
6. `MathematischAuswertbareMethode` kennzeichnet Methoden, die der Mathematikkern durch Bindung mathematischer Argumente auswerten darf.
7. Der allgemeine Methodenaufruf führt nur `MathematischAuswertbareMethode` mathematisch aus. Andere Methodenwerte werden an dieser Grenze nicht durch Termsubstitution interpretiert.
8. Bestehende Aufrufe `Methode(...)` bleiben über quellkompatible Fabrikfunktionen erhalten und erzeugen `MathematischeMethode`.
9. Bestehende mathematische Spezialoperationen erhalten während der Migration explizite Adapter auf `MathematischeMethode`; fremde Methoden liefern dabei einen fachlich benannten Capability-Fehler statt einer zufälligen Typumwandlung.
10. Das bestehende `.matlas`-Format wird nicht allein aufgrund des Kotlin-Typrefactors erhöht, weil berechnete Methodenobjekte keine persistierten Laufzeitobjekte sind.

## Abweichung von der ursprünglichen G0.1-Skizze

`Methode` bleibt in G0.1 vorerst indirekt ein `MathematischesObjekt`.

Grund: Der aktuelle gemeinsame Kartenruntime-Wertkanal (`BedingterWert.objekt`, Auswerter und zahlreiche Knotenverträge) transportiert ausschließlich `MathematischesObjekt`. Eine vollständige Trennung würde deshalb nicht nur das Methodenmodell, sondern das allgemeine Atlas-Typ-/Wertmodell ändern.

Diese Trennung wird G0.2 zugeordnet. G0.1 trennt bereits die entscheidende Semantik: Eine Methode ist nicht automatisch mathematisch signaturtragend oder mathematisch ausführbar.

## Zielhierarchie nach G0.1

```text
MathematischesObjekt                 // bis G0.2 gemeinsamer Wertkanal
        ^
        |
     Methode                         // offener Oberbegriff
        |
        +-- SignaturtragendeMethode
              |
              +-- MathematischAuswertbareMethode
                      |
                      +-- MathematischeMethode
```

Eine spätere Engine-/Scriptmethode kann zunächst direkt `Methode` implementieren, ohne `vorschrift`, mathematische Wertevorräte oder mathematische Auswertung zu erfinden. G0.2 ersetzt anschließend die mathematische Signatur-Capability durch den allgemeinen Typkern.

## Kompatibilität

Die öffentliche Konstruktorform bleibt erhalten:

```kotlin
val f: Methode = Methode(
    name = "f",
    parameter = ...,
    vorschrift = ...,
    zielMenge = ...,
)
```

Der Ausdruck erzeugt nun eine `MathematischeMethode`. Dadurch müssen bestehende Knoten, Tests und Operatorimplementierungen nicht nur wegen des Refactors ihre Konstruktorstellen umbenennen.

Historische Mehrfachausgaben bleiben ausschließlich als Lademigrations-/Testkonstruktor erhalten.

## Sicherheitsgrenze der Auswertung

Nicht mehr zulässig ist die implizite Regel:

```text
objekt is Methode
=> mathematisch durch Substitution ausführen
```

Stattdessen gilt:

```text
objekt is MathematischAuswertbareMethode
=> mathematische Anwendung zulässig

objekt is Methode
=> nur Methodenidentität garantiert
```

Damit kann eine spätere `ScriptMethod` zustandsverändernde oder Engine-spezifische Semantik besitzen, ohne vom Mathematikadapter versehentlich als reine Funktion ausgewertet zu werden.

## Verifikation

G0.1 erhält einen modulübergreifenden Regressionstest im `MathematikKartenAdapter`. Dort wird ein neuer `FremdMethode`-Typ definiert, der ausschließlich `Methode` implementiert. Der Test beweist:

- Implementierung außerhalb des Mathematikkerns ist möglich,
- die Minimaldarstellung bleibt nutzbar,
- der Typ besitzt keine mathematische Auswertungs-Capability,
- ein mathematischer Aufruf wird mit einem eindeutigen Capability-Fehler abgelehnt,
- bestehende `Methode(...)`-Konstruktion erzeugt weiterhin eine mathematisch auswertbare Implementierung.

Der Architekturguard `scripts/pruefe_methodenmodell.py` verhindert künftig erneut eine geschlossene `class/data class Methode` und prüft den Capability-basierten Methodenaufruf.

## Folgen für G0.2

G0.2 kann nun separat lösen:

- allgemeine nicht rein mathematische Atlas-Werte,
- allgemeine Methodensignaturen mit mathematischen und externen Typen,
- Typdeskriptoren für `R`, Tupel, Tensoren, `Node3D`, Ressourcen und Oder-Typen,
- Anschluss-Minigrafiken,
- Entfernung der verbleibenden mathematischen Übergangsadapter auf dem allgemeinen `Methode`-Vertrag.
